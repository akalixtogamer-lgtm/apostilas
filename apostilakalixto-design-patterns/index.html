Parte 1

Fundamentos

Antes de correr para os padrões, a gente constrói o chão: de onde eles vieram, que dor resolvem, a POO que sustenta tudo e os princípios SOLID que são a "gramática" do bom projeto.

Parte 1 · Capítulo 1

O que são Design Patterns

Um design pattern (padrão de projeto) é uma solução testada e reaproveitável para um problema que aparece de novo e de novo no projeto de software. Não é um código pronto para copiar — é uma receita de como organizar suas classes e objetos.

≈Padrão é planta de casa, não casa pronta

Um arquiteto não desenha cada casa do zero. Ele tem plantas reaproveitáveis: "casa térrea com quintal", "sobrado geminado". A planta resolve o problema estrutural; cada construtor adapta acabamento, cor e tamanho. Um design pattern é a planta — você adapta ao seu código.

De onde os padrões vieram

A ideia de "padrão" nasceu fora da computação. Em 1977, o arquiteto Christopher Alexander publicou A Pattern Language, catalogando soluções recorrentes de arquitetura de cidades e prédios. A sacada dele: bons problemas se repetem, então boas soluções podem ser nomeadas, documentadas e reutilizadas.

Nos anos 1990, quatro engenheiros levaram essa ideia para a Orientação a Objetos e mudaram a história do software.

O Gang of Four (GoF)

Em 1994, quatro autores publicaram o livro que virou a bíblia do tema: Design Patterns: Elements of Reusable Object-Oriented Software. Eles ficaram conhecidos como Gang of Four — a "Gangue dos Quatro":

AutorContribuição
Erich GammaMais tarde co-criou o JUnit e o editor que virou o VS Code.
Richard HelmPesquisador de modelagem orientada a objetos.
Ralph JohnsonProfessor, referência em frameworks e refatoração.
John VlissidesPesquisador da IBM, faleceu em 2005.

O livro catalogou 23 padrões, divididos em três famílias (criacionais, estruturais e comportamentais). Esses 23 são o nosso roteiro.

?22 ou 23?

Alguns catálogos modernos (como o refactoring.guru) listam 22 padrões "do dia a dia" e deixam o Interpreter de fora por ser raro. O livro original do GoF tem 23 — e nós vamos cobrir todos eles, incluindo o Interpreter, para você não ficar com buraco na formação.

Por que isso importa para você

  • Vocabulário comum: dizer "isso aqui é um Observer" comunica em 2 segundos o que levaria 5 minutos para explicar.
  • Soluções maduras: você reaproveita décadas de tentativa e erro de gente muito experiente.
  • Código que aguenta mudança: padrões otimizam justamente para o que mais dói no software — a mudança de requisitos.
  • Carreira: é assunto garantido em entrevista e pré-requisito para arquitetura.
◈Resumo do capítulo
  • Design pattern = solução recorrente e reaproveitável, não código pronto.
  • A ideia veio da arquitetura (Christopher Alexander) e chegou ao software pelo Gang of Four em 1994.
  • O GoF catalogou 23 padrões em 3 famílias.
  • O valor real é vocabulário comum + soluções maduras + código preparado para mudança.

Parte 1 · Capítulo 2

O problema antes dos padrões

Para valorizar a cura, primeiro a doença. Antes de pensar em estrutura, programava-se "no impulso" — e o resultado tem nome: código espaguete.

Os quatro vilões

VilãoO que éSintoma
Código espagueteFluxo embaralhado, tudo conectado com tudo.Você muda uma linha e quebra três telas distantes.
Acoplamento excessivoUma classe depende dos detalhes internos de muitas outras.Não dá para reusar nada isoladamente.
DuplicaçãoO mesmo trecho copiado e colado em N lugares.Corrigir um bug exige caçar 7 cópias.
Baixa manutençãoMedo de mexer no código."Funciona, não encosta."

Vendo a dor no código

Imagine um sistema de pagamentos escrito sem nenhum cuidado de projeto. Tudo num método só, decidindo o tipo de pagamento com if/else e repetindo regras:

java · antes (ruim)
public class Checkout {
    public void pagar(String tipo, double valor) {
        if (tipo.equals("pix")) {
            // valida, gera QR, registra, envia e-mail...
            System.out.println("Pagando " + valor + " via Pix");
        } else if (tipo.equals("credito")) {
            // valida cartao, antifraude, parcela, registra, envia e-mail...
            System.out.println("Pagando " + valor + " no credito");
        } else if (tipo.equals("boleto")) {
            // gera linha digitavel, registra, envia e-mail...
            System.out.println("Pagando " + valor + " via boleto");
        }
        // E quando entrar Apple Pay? Mais um else-if aqui dentro.
        // E o envio de e-mail repetido em cada ramo? Duplicacao.
    }
}
!Por que isso é uma bomba-relógio

Toda vez que surge um novo meio de pagamento, você edita a classe Checkout. Isso viola o princípio do "aberto para extensão, fechado para modificação" (vamos ver no Cap. 4). Quanto mais cresce, mais frágil fica. Padrões como Strategy e Factory existem exatamente para matar esse if/else gigante.

O custo invisível

Código ruim não cobra a conta no dia que é escrito — cobra meses depois, quando o time gasta o dobro do tempo para entregar metade. Isso tem nome em engenharia: dívida técnica. Padrões são uma forma de manter essa dívida sob controle.

◈Resumo do capítulo
  • Antes dos padrões, dominavam espaguete, acoplamento, duplicação e baixa manutenção.
  • O sintoma clássico: mexer num ponto quebra outro distante.
  • O if/else gigante que decide "tipo" é o cheiro de código mais comum — e o mais fácil de melhorar.
  • Código ruim gera dívida técnica: a conta chega depois, com juros.

Parte 1 · Capítulo 3

Conceitos obrigatórios de POO

Padrões são feitos de Orientação a Objetos. Se algum termo abaixo estiver nebuloso, este capítulo é o seu chão firme. Vamos rápido, mas sem pular ninguém.

Classe e objeto

A classe é o molde; o objeto é o que sai do molde. A classe Carro define que todo carro tem cor e velocidade; cada carro que você cria é um objeto independente.

java
public class Carro {          // a classe: o molde
    String cor;
    int velocidade;
}

Carro fusca = new Carro();    // objeto 1 (instancia)
Carro civic = new Carro();    // objeto 2, independente
fusca.cor = "azul";

Encapsulamento

Esconder os detalhes internos e expor só o necessário. Atributos ficam private; o acesso passa por métodos. Assim você protege o objeto de estados inválidos.

java
public class ContaBancaria {
    private double saldo;                 // ninguem mexe direto

    public void depositar(double v) {
        if (v > 0) saldo += v;            // regra protegida aqui dentro
    }
    public double getSaldo() { return saldo; }
}

Herança

Uma classe filha reaproveita o que a classe mãe já tem, usando extends. Bom para "é um tipo de": um Gato é um Animal.

java
public class Animal {
    public void respirar() { System.out.println("respirando..."); }
}
public class Gato extends Animal {        // Gato herda respirar()
    public void miar() { System.out.println("miau"); }
}

Polimorfismo

"Muitas formas." O mesmo método se comporta diferente dependendo do objeto real. É o coração de quase todo padrão.

java
Animal a = new Gato();   // referencia Animal, objeto Gato
a.emitirSom();           // chama a versao de Gato em tempo de execucao

Abstração

Focar no o quê e esconder o como. Você usa List sem saber se por dentro é array ou lista ligada. A abstração é a "interface mental" da coisa.

Interface

Um contrato: define o que uma classe deve fazer, sem dizer como. Quem implementa é obrigado a cumprir.

java
public interface Pagavel {
    void pagar(double valor);   // contrato, sem corpo
}
public class Pix implements Pagavel {
    public void pagar(double valor) { /* implementacao do Pix */ }
}

Classe abstrata

Um meio-termo: pode ter método pronto e método sem corpo (abstract). Não pode ser instanciada; serve de base para filhas.

java
public abstract class Forma {
    public abstract double area();          // filha decide
    public void descrever() {               // pronto, herdado
        System.out.println("Area = " + area());
    }
}
★Interface x Classe abstrata

Interface = só contrato (em Java moderno aceita método default, mas pense nela como "o quê"). Classe abstrata = contrato + comportamento parcial compartilhado. Regra prática: precisa só de capacidade → interface; precisa compartilhar código entre filhas → classe abstrata.

As quatro relações entre classes

Padrões e UML falam o tempo todo destas relações. Decore a diferença pela "força do laço":

RelaçãoSignificadoExemploForça do laço
DependênciaUma usa a outra de passagem (parâmetro/variável local).Um método recebe um Logger.Fraca
AssociaçãoUma conhece a outra de forma duradoura (atributo).Professor tem uma Turma.Média
Agregação"Tem um", mas as partes vivem sem o todo.Time tem Jogadores (que existem fora do time).Média/forte
Composição"Tem um", e as partes morrem com o todo.Casa tem Cômodos (sem casa, sem cômodo).Forte
relações em texto
Dependencia:  A ---->  B     (A usa B momentaneamente)
Associacao:   A ----  B      (A tem referencia para B)
Agregacao:    A <>--- B      (A "tem" B; B sobrevive sozinho)  [losango vazado]
Composicao:   A <#>-- B      (A "tem" B; B morre com A)         [losango cheio]

Composição > herança

Um dos mantras do GoF: "prefira composição a herança". Em vez de herdar tudo de uma mãe (laço rígido), monte o objeto combinando peças menores (laço flexível). Quase todo padrão estrutural e comportamental aplica isso.

◈Resumo do capítulo
  • Classe é molde, objeto é instância.
  • Os 4 pilares: encapsulamento (esconder), herança (reaproveitar), polimorfismo (muitas formas), abstração (o quê, não o como).
  • Interface = contrato puro; classe abstrata = contrato + código compartilhado.
  • Dependência < associação < agregação < composição (do laço mais fraco ao mais forte).
  • Mantra do GoF: prefira composição a herança.

Entrega: as 3 classificações com justificativa.
◇Quiz — POO essencial
Qual pilar permite que a.emitirSom() rode versões diferentes conforme o objeto real?
Isso! Polimorfismo é o mesmo método assumindo formas diferentes em tempo de execução.
Quase. Encapsulamento é esconder estado; o que muda o comportamento conforme o objeto é o polimorfismo.

Exato. Parte que morre com o todo = composição (losango cheio).
Na agregação as partes sobrevivem sozinhas. Aqui elas morrem com o todo → composição.
Você precisa apenas garantir que várias classes saibam "pagar(valor)", sem compartilhar código. Use:
Boa. Só contrato, sem código compartilhado → interface.
Se não há código a compartilhar, classe abstrata é exagero. O contrato puro é uma interface.

SOLID — a gramática do bom projeto

SOLID são cinco princípios que mantêm o código flexível e fácil de manter. Eles não são padrões, mas são o porquê por trás de quase todos. Se você entender SOLID, os padrões deixam de ser mágica.

LetraPrincípioEm uma frase
SSingle ResponsibilityUma classe, um motivo para mudar.
OOpen/ClosedAberto para extensão, fechado para modificação.
LLiskov SubstitutionFilho deve poder substituir o pai sem surpresas.
IInterface SegregationMuitas interfaces pequenas > uma gigante.
DDependency InversionDependa de abstrações, não de implementações.

S — Single Responsibility (Responsabilidade Única)

Uma classe deve ter um único motivo para mudar. Se ela cuida de regra de negócio e de e-mail e de banco, qualquer um dos três a obriga a mudar.

java · errado
public class Relatorio {
    public String gerar() { /* monta o relatorio */ return "..."; }
    public void salvarEmDisco(String s) { /* I/O de arquivo */ }
    public void enviarPorEmail(String s) { /* SMTP */ }
}
// Tres responsabilidades: conteudo, persistencia e envio.
java · correto
public class Relatorio {            // so o conteudo
    public String gerar() { return "..."; }
}
public class ArquivoSalvador {     // so persistencia
    public void salvar(String s) { /* ... */ }
}
public class EmailSender {         // so envio
    public void enviar(String s) { /* ... */ }
}

O — Open/Closed (Aberto/Fechado)

Você deve poder adicionar comportamento sem editar o código existente. Lembra do if/else de pagamentos? Cada novo meio te obriga a abrir a classe. Isso é fechado para extensão e aberto para modificação — o oposto do ideal.

java · correto (via abstração)
public interface MeioPagamento { void pagar(double v); }

public class Pix    implements MeioPagamento { public void pagar(double v){} }
public class Cartao implements MeioPagamento { public void pagar(double v){} }
// Novo meio? Crie uma classe nova. O Checkout NAO muda.
★O é a alma dos padrões criacionais

Quase todo padrão que veremos na Parte 3 existe para honrar o Open/Closed: permitir novas variações de objeto sem reescrever o que já funciona.

L — Liskov Substitution (Substituição de Liskov)

Se B é filho de A, então usar um B onde se espera um A não pode quebrar nada. O exemplo clássico do mau uso: Quadrado extends Retangulo. Faz sentido na geometria, mas no código o quadrado quebra a expectativa de "mudar largura e altura de forma independente".

java · viola Liskov
class Retangulo {
    protected int l, a;
    public void setLargura(int l){ this.l = l; }
    public void setAltura(int a){ this.a = a; }
    public int area(){ return l * a; }
}
class Quadrado extends Retangulo {
    public void setLargura(int l){ this.l = l; this.a = l; } // forca a==l
    public void setAltura(int a){ this.l = a; this.a = a; }  // surpresa!
}
// Um codigo que espera Retangulo e faz set(2x5) esperando area 10
// recebe 25 com Quadrado. O filho NAO pode substituir o pai.

I — Interface Segregation (Segregação de Interface)

Ninguém deve ser obrigado a implementar métodos que não usa. Prefira várias interfaces pequenas a uma "interface gorda".

java · errado
public interface Funcionario {
    void trabalhar();
    void receberSalario();
    void tirarFerias();   // e um Robo? robo nao tira ferias.
}
java · correto
public interface Trabalhador { void trabalhar(); }
public interface Assalariado { void receberSalario(); }
// cada classe implementa so o que faz sentido para ela

D — Dependency Inversion (Inversão de Dependência)

Módulos importantes não devem depender de detalhes; ambos dependem de abstrações. Em vez de o Pedido criar diretamente um MySQLRepo, ele recebe um Repositorio (interface).

java · correto
public interface Repositorio { void salvar(Object o); }

public class ServicoPedido {
    private final Repositorio repo;
    public ServicoPedido(Repositorio repo) { this.repo = repo; } // injetado
    public void finalizar(Object pedido) { repo.salvar(pedido); }
}
// Trocar MySQL por Mongo nao muda o ServicoPedido. So a implementacao do repo.
✓DI vs IoC vs Spring

Esse "receber de fora em vez de criar dentro" é a Injeção de Dependência. Frameworks como Spring fazem isso automaticamente (Inversão de Controle). Você vai reencontrar esse princípio em vários padrões e no Volume 4.

◈Resumo do capítulo
  • SOLID = 5 princípios que mantêm o código flexível: S.O.L.I.D.
  • S: um motivo para mudar. O: estenda sem editar. L: filho substitui pai sem surpresa.
  • I: interfaces pequenas e focadas. D: dependa de abstrações.
  • SOLID é o "porquê" dos padrões — entenda isto e os 23 padrões fazem sentido sozinhos.

java · ponto de partida
public class Usuario {

"Adicionar um novo tipo sem editar o código que já existe" é a ideia de qual letra?
Certo. Open/Closed: aberto para extensão, fechado para modificação.
Reveja: estender sem modificar é o O de Open/Closed.
Uma interface Funcionario que obriga um robô a implementar tirarFerias() viola:
Isso. Interface gorda forçando método inútil → quebra o I.

Receber um Repositorio (interface) pelo construtor em vez de dar new MySQLRepo() dentro da classe é aplicar:

Parte 2 · Capítulo 5

O que é um pattern (de verdade)

Um padrão não é uma biblioteca nem um trecho de código que você importa. É a descrição de uma solução para um problema recorrente, que você adapta ao seu contexto.

★A equação para nunca esquecer

Pattern ≠ código pronto.   Pattern = solução recorrente + estrutura + nome. Dois desenvolvedores podem implementar o mesmo padrão com códigos diferentes — e ainda assim ser o mesmo padrão.

Do que um padrão é feito

No livro do GoF, todo padrão é descrito por quatro elementos. Você vai reconhecê-los em cada capítulo desta apostila:

ElementoO que responde
NomeComo chamamos? (entra no vocabulário do time)
ProblemaQuando aplicar? Que situação ele resolve?
SoluçãoQuais classes/objetos e como se relacionam (a estrutura).
ConsequênciasO que ganho e o que pago ao usar (trade-offs).

Benefícios — e o aviso

Padrões trazem reuso de soluções maduras, vocabulário comum e código preparado para mudança. Mas há um porém honesto:

!Padrão não é troféu

O maior erro de iniciante é forçar padrões para parecer sofisticado. Padrão aplicado sem necessidade vira complexidade gratuita. A pergunta certa nunca é "qual padrão eu uso aqui?", e sim "qual problema eu tenho?". O padrão é resposta, não ponto de partida.

◈Resumo do capítulo
  • Pattern é solução descrita e adaptável, não código importável.
  • Todo padrão tem nome, problema, solução (estrutura) e consequências.
  • Benefícios: reuso, vocabulário comum, flexibilidade.
  • Aviso: padrão sem problema real = complexidade desnecessária.

Cinco padrões que tratam de uma coisa só: criar objetos sem amarrar seu código a classes concretas. Cada um segue a mesma receita didática — conceito, analogia, problema, solução, código comentado, erros, quando usar/evitar, exercício e desafio.

Parte 3 · Criacional

Singleton

Conceito: garante que uma classe tenha uma única instância em todo o sistema e oferece um ponto global de acesso a ela.

≈O presidente do país

Por mais que existam milhões de cidadãos, há um presidente por vez. Não importa quem pergunte "quem é o presidente?", a resposta aponta sempre para a mesma pessoa. O Singleton é isso: por mais que o código peça a instância, recebe sempre a mesma.

Problema

Alguns recursos devem existir uma vez só: a configuração da aplicação, um pool de conexões, um logger central. Se cada parte do código criar o seu próprio, você gasta memória à toa e — pior — pode ter estados inconsistentes (dois loggers escrevendo em arquivos diferentes).

Solução

A própria classe controla sua criação: o construtor vira private (ninguém de fora dá new) e um método estático devolve sempre a mesma instância guardada internamente.

estrutura
+------------------------------+
|          Singleton           |
+------------------------------+
| - instancia : Singleton      |  <-- guarda a si mesma (static)
| - Singleton()                |  <-- construtor PRIVADO
+------------------------------+
| + getInstancia() : Singleton |  <-- ponto de acesso global
+------------------------------+

Código Java comentado

java · thread-safe (holder)
public class Configuracao {

    // 1) Construtor privado: impede "new Configuracao()" de fora.
    private Configuracao() {
        // carrega config de arquivo, etc.
    }

    // 2) Holder estatico: a JVM so carrega esta classe interna
    //    na primeira vez que getInstancia() e chamado, e faz isso
    //    de forma thread-safe automaticamente.
    private static class Holder {
        private static final Configuracao INSTANCIA = new Configuracao();
    }

    // 3) Ponto de acesso global. Sempre devolve a MESMA instancia.
    public static Configuracao getInstancia() {
        return Holder.INSTANCIA;
    }

    public String get(String chave) { return "valor"; }
}

// Uso:
Configuracao c1 = Configuracao.getInstancia();
Configuracao c2 = Configuracao.getInstancia();
// c1 == c2  -> true (mesmo objeto)
✓Por que o "Holder"?

A versão ingênua (if (instancia == null) instancia = new ...) quebra com várias threads: duas podem entrar no if ao mesmo tempo e criar dois objetos. O padrão Initialization-on-demand Holder resolve isso de graça, usando a garantia da JVM de que classes carregam uma vez só, com segurança de thread.

Em outras linguagens

csharp
public sealed class Configuracao {
    private static readonly Configuracao _inst = new Configuracao();
    private Configuracao() { }
    public static Configuracao Instancia => _inst;
}
python
class Configuracao:
    _inst = None
    def __new__(cls):
        if cls._inst is None:
            cls._inst = super().__new__(cls)
        return cls._inst   # sempre o mesmo objeto
javascript
// Em JS, um modulo ja e um singleton natural:
let instancia;
export function getConfig() {
  if (!instancia) instancia = { tema: "neon" };
  return instancia;
}

Erros comuns

  • Virar variável global disfarçada: usar Singleton para acessar estado de qualquer lugar acopla tudo a ele. É o "padrão" mais abusado.
  • Esquecer threads: a versão lazy ingênua não é thread-safe.
  • Dificultar testes: estado global compartilhado entre testes causa falhas fantasmas.
Quando usarQuando evitar
Há de fato um único recurso lógico (config, logger, pool).Você só quer "acessar de qualquer lugar" — isso é estado global, não Singleton.
O acesso global simplifica e não esconde dependências.A classe guarda estado mutável que atrapalha testes.
Criar o objeto é caro e você quer reaproveitar.Você poderia simplesmente injetar a dependência (geralmente melhor).

◇Quiz — Singleton
O que torna o construtor de um Singleton especial?
Certo. Construtor privado impede que outros criem instâncias com new.
O segredo é o construtor privado: só a própria classe pode se instanciar.
Qual é a crítica mais comum ao Singleton?
Exato. Abusado, ele acopla o sistema todo e prejudica testes.
A dor real não é desempenho: é virar estado global, acoplando tudo e travando testes.

Factory Method

Conceito: define um método para criar objetos, mas deixa as subclasses decidirem qual classe concreta instanciar. Você cria "produtos" sem dar new da classe concreta no meio do código.

≈A fábrica de documentos

Você pede ao seu editor "novo documento". Dependendo do programa, sai um .docx, um .pdf ou um .txt. Você não diz como criar — você pede, e a fábrica certa entrega o produto certo. O new fica escondido dentro da fábrica.

Problema

Aquele if/else do Capítulo 2 espalhava new Pix(), new Cartao() pelo código. Toda vez que surge um tipo novo, você caça e edita todos esses pontos. Isso viola o Open/Closed.

Solução

Centralize a criação em um método fábrica. O código cliente conversa com a interface do produto; a decisão de qual concreto criar mora num único lugar.

estrutura
   <>            Criador (abstrato)
    Transporte      <----   + criar() : Transporte   (factory method)
        ^                          ^
   +----+----+              +------+------+
 Carro     Navio        CriadorCarro   CriadorNavio
 (produtos concretos)   (sobrescrevem criar())

Código Java comentado

java
// 1) Produto: a interface que o cliente conhece.
public interface Transporte {
    void entregar();
}

// 2) Produtos concretos.
public class Carro implements Transporte {
    public void entregar() { System.out.println("Entrega por terra"); }
}
public class Navio implements Transporte {
    public void entregar() { System.out.println("Entrega por mar"); }
}

// 3) Criador: declara o factory method (aqui, abstrato).
public abstract class Logistica {
    public abstract Transporte criarTransporte();   // FACTORY METHOD

    // Reaproveita o produto sem saber qual concreto e:
    public void planejar() {
        Transporte t = criarTransporte();  // delega a decisao
        t.entregar();
    }
}

// 4) Criadores concretos decidem o produto.
public class LogisticaRodoviaria extends Logistica {
    public Transporte criarTransporte() { return new Carro(); }
}
public class LogisticaMaritima extends Logistica {
    public Transporte criarTransporte() { return new Navio(); }
}

// Uso: o cliente escolhe a fabrica, nao o produto.
Logistica log = new LogisticaMaritima();
log.planejar();   // "Entrega por mar"
★A virada de chave

Repare: o método planejar() usa Transporte sem nunca escrever new Carro() ou new Navio(). Para adicionar entrega aérea, você cria Aviao + LogisticaAerea e não toca em nada que já existe. Isso é o Open/Closed em ação.

Versão simples (factory estática)

Na prática, muito código usa uma variação enxuta: um único método estático que devolve o produto conforme um parâmetro. Tecnicamente é uma "Simple Factory", mas resolve 80% dos casos.

java · simple factory
public class TransporteFactory {
    public static Transporte criar(String tipo) {
        return switch (tipo) {
            case "carro" -> new Carro();
            case "navio" -> new Navio();
            default -> throw new IllegalArgumentException("tipo invalido");
        };
    }
}
Transporte t = TransporteFactory.criar("carro");

Erros comuns

  • Confundir com Abstract Factory (este cria um produto; o Abstract cria famílias).
  • Deixar o switch da Simple Factory crescer sem fim — às vezes Strategy ou um mapa resolve melhor.
  • Criar fábrica para algo trivial: se só existe um tipo, não precisa de fábrica.
Quando usarQuando evitar
Você não sabe de antemão quais tipos concretos precisará criar.Só existe um tipo de produto e não vai mudar.
Quer isolar a criação para honrar o Open/Closed.O custo da indireção supera o ganho (over-engineering).
Frameworks que deixam você "plugar" suas próprias classes.Um simples construtor já resolveria com clareza.
intermediárioExercício — Fábrica de notificações

◈Resumo do capítulo
  • Factory Method delega a criação de UM produto para subclasses/fábricas.
  • O cliente fala com a interface do produto; o new fica escondido.
  • Honra o Open/Closed: novo tipo = nova classe, sem editar o existente.
  • A "Simple Factory" (método estático com switch) é a variação prática mais comum.

Abstract Factory

Conceito: cria famílias de objetos relacionados sem especificar suas classes concretas. É um "Factory Method elevado": em vez de um produto, uma fábrica produz um conjunto coerente de produtos.

≈Montadora de móveis por estilo

Você escolhe um estilo: "Vitoriano" ou "Moderno". Ao escolher, ganha um conjunto combinando — cadeira, sofá e mesa, todos no mesmo estilo. Você nunca mistura cadeira vitoriana com mesa moderna. A fábrica garante a coerência da família.

Problema

Seu app precisa de temas (claro/escuro). Cada tema tem botão, caixa de texto e menu próprios. Se você criar cada componente com if (tema == escuro) espalhado, vai acabar com um botão escuro dentro de um menu claro. Você precisa garantir famílias consistentes.

Solução

estrutura
      <> FabricaUI
      + criarBotao() : Botao
      + criarCheckbox() : Checkbox
            ^                ^
   FabricaClaro          FabricaEscuro
   (Botao/CheckboxClaro) (Botao/CheckboxEscuro)
   --- cada fabrica produz a FAMILIA inteira no mesmo estilo ---
java
// Produtos abstratos (a familia)
public interface Botao   { void render(); }
public interface Checkbox{ void render(); }

// Familia CLARA
public class BotaoClaro    implements Botao    { public void render(){ System.out.println("botao claro"); } }
public class CheckboxClaro implements Checkbox { public void render(){ System.out.println("check claro"); } }
// Familia ESCURA
public class BotaoEscuro    implements Botao    { public void render(){ System.out.println("botao escuro"); } }
public class CheckboxEscuro implements Checkbox { public void render(){ System.out.println("check escuro"); } }

// A FABRICA ABSTRATA: declara como criar a familia toda.
public interface FabricaUI {
    Botao criarBotao();
    Checkbox criarCheckbox();
}
// Fabricas concretas: cada uma so produz produtos do seu estilo.
public class FabricaClara implements FabricaUI {
    public Botao criarBotao()       { return new BotaoClaro(); }
    public Checkbox criarCheckbox() { return new CheckboxClaro(); }
}
public class FabricaEscura implements FabricaUI {
    public Botao criarBotao()       { return new BotaoEscuro(); }
    public Checkbox criarCheckbox() { return new CheckboxEscuro(); }
}

// Cliente: recebe UMA fabrica e monta a tela inteira coerente.
public class Tela {
    private final Botao botao;
    private final Checkbox checkbox;
    public Tela(FabricaUI f) {        // injeta a familia escolhida
        this.botao = f.criarBotao();
        this.checkbox = f.criarCheckbox();
    }
    public void desenhar() { botao.render(); checkbox.render(); }
}

// Uso:
FabricaUI fabrica = new FabricaEscura();  // troca aqui muda a tela toda
new Tela(fabrica).desenhar();             // tudo escuro, sem mistura
★Factory Method x Abstract Factory

Factory Method cria um produto e usa herança (subclasse decide). Abstract Factory cria uma família de produtos e usa composição (você passa a fábrica). Regra: um produto → Factory Method; um conjunto coerente → Abstract Factory.

Erros comuns

  • Usar quando só há um produto na "família" (aí é Factory Method, ou nem isso).
  • Adicionar um produto novo à família: exige mexer em todas as fábricas. É o preço do padrão.
Quando usarQuando evitar
Há famílias de produtos que devem combinar entre si.Só existe um produto, sem "família".
Você quer trocar a família inteira num ponto único.As famílias raramente mudam — indireção sem retorno.
Temas, drivers de banco por fornecedor, UIs por SO.Adicionar produtos novos é frequente (custo alto de manutenção).
avançadoDesafio — Fábrica de banco de dados

Modele uma família por fornecedor: Conexao e Comando, com implementações MySQL* e Postgres*. Crie FabricaMySQL e FabricaPostgres implementando FabricaBanco. Mostre um cliente que recebe a fábrica e roda um comando — trocando só a fábrica para mudar de banco.

Entrega: produtos + 2 fábricas + cliente que troca de fornecedor numa linha.
◇Quiz — Abstract Factory
A diferença central entre Factory Method e Abstract Factory é:
Isso. Factory Method = um produto (herança); Abstract Factory = família (composição).
A questão é escopo: um produto vs. uma família coerente de produtos.
◈Resumo do capítulo
  • Abstract Factory cria famílias de objetos que precisam combinar.
  • Garante coerência: nunca mistura produtos de famílias diferentes.
  • Usa composição (passa-se a fábrica); Factory Method usa herança.
  • Custo: adicionar um produto novo obriga mexer em todas as fábricas.

Builder

Conceito: constrói um objeto complexo passo a passo, separando a montagem da representação final. Ideal quando há muitos parâmetros, vários opcionais.

≈Montando um lanche

No balcão você fala: "pão, hambúrguer, sem cebola, com queijo extra, sem molho". Você monta o lanche passo a passo, escolhendo só o que quer. No fim, recebe o lanche pronto. O Builder é esse balcão para objetos.

Problema — o construtor telescópico

Quando um objeto tem muitos campos opcionais, o construtor vira um monstro impossível de ler:

java · dor
// O que cada valor significa? Boa sorte.
Pizza p = new Pizza("grande", true, false, true, true, false, 2);

Solução

estrutura
  Cliente ---> PizzaBuilder.tamanho(...).comQueijo()....build()
                     |                                     |
                     +---- monta passo a passo ------------+--> Pizza pronta
java · builder fluente
public class Pizza {
    private final String tamanho;      // obrigatorio
    private final boolean queijo;      // opcionais...
    private final boolean calabresa;
    private final boolean borda;

    // Construtor PRIVADO: so o builder cria.
    private Pizza(Builder b) {
        this.tamanho   = b.tamanho;
        this.queijo    = b.queijo;
        this.calabresa = b.calabresa;
        this.borda     = b.borda;
    }

    // O Builder vive dentro da Pizza (classe estatica aninhada).
    public static class Builder {
        private final String tamanho;          // obrigatorio no construtor do builder
        private boolean queijo, calabresa, borda;

        public Builder(String tamanho) { this.tamanho = tamanho; }

        // Cada metodo devolve "this" -> permite encadear (fluent).
        public Builder comQueijo()    { this.queijo = true; return this; }
        public Builder comCalabresa() { this.calabresa = true; return this; }
        public Builder comBorda()     { this.borda = true; return this; }

        public Pizza build() { return new Pizza(this); }  // entrega o objeto
    }
}

// Uso: legivel, so o que importa, em qualquer ordem.
Pizza p = new Pizza.Builder("grande")
        .comQueijo()
        .comBorda()
        .build();
★Por que cada método retorna this?

Retornar a própria instância do builder permite o encadeamento fluente (.comQueijo().comBorda()). É o que transforma uma criação confusa numa frase quase em português.

Erros comuns

  • Usar Builder para objetos simples com 2-3 campos — aí o construtor normal é mais claro.
  • Esquecer de validar no build() (ex.: tamanho obrigatório nulo).
  • Confundir com Factory: Factory escolhe qual objeto; Builder define como montar um objeto complexo.
Quando usarQuando evitar
Muitos parâmetros, vários opcionais.Objeto simples com poucos campos.
Quer criação legível e imutável.A criação já é clara com um construtor.
Variações de montagem do mesmo produto.Você precisa escolher entre tipos diferentes (use Factory).
intermediárioExercício — Builder de Usuário

avançadoDesafio — Director

◈Resumo do capítulo
  • Builder monta objetos complexos passo a passo, separando montagem de resultado.
  • Mata o "construtor telescópico" e permite imutabilidade.
  • Métodos retornam this para encadeamento fluente.
  • Builder = como montar; Factory = qual criar.

Prototype

Conceito: cria novos objetos clonando um objeto existente (o protótipo), em vez de instanciar do zero. Útil quando criar é caro ou quando você quer copiar um estado já configurado.

≈Ctrl+C, Ctrl+V de um documento modelo

Você tem um documento-modelo todo formatado. Para um novo, você duplica o modelo e altera o conteúdo — em vez de formatar tudo de novo. O Prototype é esse "duplicar e ajustar".

Problema

Montar um objeto pode ser caro (consulta a banco, cálculo pesado, muitos passos). Se você precisa de vários parecidos, refazer tudo a cada vez é desperdício. Além disso, às vezes você só tem o objeto em mãos e nem conhece a classe concreta para dar new.

Solução

estrutura
  <> Prototipo
  + clonar() : Prototipo
        ^
   FormaConcreta  ---- clonar() devolve uma COPIA de si mesma
java
// 1) Contrato de clonagem.
public interface Prototipo {
    Prototipo clonar();
}

// 2) Objeto clonavel: o clone copia o estado atual.
public class Personagem implements Prototipo {
    private String nome;
    private int nivel;
    private int[] atributos;   // cuidado: referencia!

    public Personagem(String nome, int nivel, int[] atributos) {
        this.nome = nome; this.nivel = nivel; this.atributos = atributos;
    }

    public Prototipo clonar() {
        // Copia PROFUNDA do array para o clone nao compartilhar o mesmo.
        int[] copia = atributos.clone();
        return new Personagem(this.nome, this.nivel, copia);
    }

    public void setNome(String n) { this.nome = n; }
}

// Uso: configura uma vez, clona varias.
Personagem base = new Personagem("Guerreiro", 10, new int[]{8,5,3});
Personagem novo = (Personagem) base.clonar();
novo.setNome("Guerreiro 2");  // nao afeta o "base"
!Cópia rasa x cópia profunda

O erro nº 1 do Prototype: copiar só as referências (cópia rasa). Aí o clone e o original compartilham a mesma lista/array — mexer em um bagunça o outro. Sempre pergunte: meus campos são objetos mutáveis? Se sim, faça cópia profunda (clone os objetos internos também).

Erros comuns

  • Cópia rasa onde precisava de profunda (bug silencioso e cruel).
  • Depender do Cloneable de Java, que é problemático — prefira um método clonar() próprio, como acima.
  • Usar Prototype quando um construtor simples já resolveria.
Quando usarQuando evitar
Criar do zero é caro e você quer copiar estado pronto.Criar é barato e direto.
Você só tem a instância, não a classe concreta.Objetos com grafos de referência muito complexos (clone vira pesadelo).
Precisa de muitas variações de um objeto base.Imutáveis — não precisa clonar o que não muda.
avançadoDesafio — Editor com clone

Modele uma Figura (com x, y, cor e uma List<Integer> pontos) que implemente clonar() com cópia profunda da lista. Crie uma figura, clone-a, altere os pontos do clone e prove (imprimindo) que o original ficou intacto.

Entrega: a classe Figura + demonstração de que o original não muda.
◈Resumo do capítulo
  • Prototype cria objetos clonando um protótipo já configurado.
  • Bom quando criar do zero é caro ou você só tem a instância.
  • O risco central é cópia rasa: faça cópia profunda de campos mutáveis.
  • Em Java, prefira um método clonar() próprio a Cloneable.
